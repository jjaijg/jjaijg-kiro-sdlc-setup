# Epic Writer Skill

## Purpose
Analyse a BRD document and produce a structured Epics & Features document following BDD conventions.

---

## Activation
This skill is activated when the user provides a BRD file and requests epic generation.
Announce activation with:
> 🟢 **Epic Writer skill activated.** Analysing BRD and generating epics…

---

## Input
- A BRD markdown file provided in chat context via `#File`

---

## Output
A markdown file saved to: `docs/[feature-name]/phase1/[feature-name]-epics.md`

Where `[feature-name]` is derived from the BRD Project Title, lowercased and hyphenated (e.g. `personal-banking-current-account` → `pbp-current-account`).

---

#### BDD Scenarios (High Level)

```gherkin
Feature: [Feature Name]

  Background:
    Given [shared precondition]

  Scenario: [Happy path]
    Given [precondition]
    When  [action]
    Then  [expected outcome]

  Scenario: [Alternate/edge case]
    Given [precondition]
    When  [action]
    Then  [expected outcome]
```

---

[Repeat for each Epic]

---

## Approval Checklist

- [ ] All business requirements from BRD are covered by at least one epic
- [ ] All in-scope items have corresponding features
- [ ] Out-of-scope items are not referenced in any epic
- [ ] BDD scenarios cover happy path and key edge cases
- [ ] Stakeholders validated against BRD stakeholder list
- [ ] Epic document reviewed by BA
- [ ] Epic document approved by PO
```

---

## Rules

1. Derive epics directly from BRD Business Requirements (BR-xxx sections). Do not invent requirements not present in the BRD.
2. Map each BR to at least one Feature under the appropriate Epic.
3. Group features logically — e.g. all account opening related BRs form one epic.
4. Write BDD scenarios at feature level using Gherkin syntax (`Feature`, `Background`, `Scenario`, `Given`/`When`/`Then`/`And`/`But`).
5. Use `Scenario Outline` + `Examples` table where multiple data variations exist.
6. Do not assume anything not stated in the BRD. If something is ambiguous, add a `⚠️ OPEN QUESTION:` comment inline and continue.
7. Non-functional requirements (NFRs) should be captured as constraints within relevant epics, not as standalone epics, unless a dedicated NFR epic is clearly warranted.
8. The Approval Checklist must always appear at the bottom of the document as unchecked items (`- [ ]`).
