# Story Writer Skill

## Purpose
Expand approved Epics & Features into detailed User Stories following BDD conventions.

---

## Activation
This skill is activated after the epic document for the feature has been approved (all checklist items marked `[x]`).
Announce activation with:
> 🟢 **Story Writer skill activated.** Generating user stories from approved epics…

---

## Pre-condition Check (MANDATORY)
Before generating stories, the agent MUST:

1. Check if `docs/[feature-name]/phase1/[feature-name]-epics.md` exists.
2. If it does NOT exist → stop and tell the BA:
   > ❌ No epic document found for this feature. Please generate and approve the epics first.
3. If it exists → check the **Approval Checklist** at the bottom of that file.
4. If ANY checklist item is NOT marked `[x]` → stop and tell the BA:
   > ❌ Epic document approval is incomplete. All checklist items must be marked as approved before stories can be generated.
5. Only proceed if ALL checklist items are `[x]`.

---

## Input
- The approved epics file: `docs/[feature-name]/phase1/[feature-name]-epics.md`

---

## Output
A markdown file saved to: `docs/[feature-name]/phase1/[feature-name]-stories.md`

---

#### Acceptance Criteria (BDD)

```gherkin
Feature: [Feature Name]

  Background:
    Given [shared precondition]

  Scenario: [Happy path title]
    Given [precondition]
    When  [action]
    Then  [expected outcome]
    And   [additional assertion]

  Scenario: [Validation / Error path]
    Given [precondition]
    When  [invalid action or missing data]
    Then  [error or rejection outcome]

  Scenario Outline: [Data-driven scenario title]
    Given [precondition with <variable>]
    When  [action with <variable>]
    Then  [outcome with <expected>]

    Examples:
      | variable | expected |
      | value1   | result1  |
      | value2   | result2  |
```

#### Definition of Done
- [ ] Code implemented and unit tested
- [ ] AC scenarios automated (BDD)
- [ ] Code reviewed and merged
- [ ] QA sign-off obtained
- [ ] No open blocker bugs

#### Notes / Dependencies
[Any dependencies on other stories, systems, or open questions]

---

[Repeat for each User Story]

---

## Approval Checklist

- [ ] All epics and features are covered by at least one user story
- [ ] Every story has a clear "As a / I want to / So that" statement
- [ ] All BDD scenarios cover happy path, validation, and edge cases
- [ ] Scenario Outlines used where multiple data inputs exist
- [ ] No story contains assumptions not traceable to the BRD or epic
- [ ] Definition of Done present on every story
- [ ] Stories reviewed by BA
- [ ] Stories approved by PO
```

---

## Rules

1. Create one or more user stories per Feature (EP-xxx-Fxx). Stories should be independently deliverable.
2. Story IDs are sequential: US-001, US-002, …
3. Every story MUST have the format: `As a [role] / I want to / So that`.  Roles come from the BRD Stakeholders section.
4. BDD scenarios MUST be written in Gherkin. Use `Scenario Outline` + `Examples` for parameterised cases.
5. Do not duplicate scenarios already covered in another story for the same feature. Cross-reference with `See US-xxx`.
6. NFR stories (performance, security, audit) should be created if an NFR directly impacts a user-facing capability.
7. Do not assume anything not in the BRD or epic doc. Inline ambiguities as `⚠️ OPEN QUESTION:`.
8. The Approval Checklist must always appear at the bottom of the document as unchecked items (`- [ ]`).
